# AGENTS.md

给 AI 的工作规则。人读的说明在 `README.md`，这份只写「必须怎么做 / 绝不能怎么做」。

## 怎么跑 Python

本机 `python` / `python3` 是 WindowsApps 假壳（退出码 49、零输出），`py` 不在 PATH。
**一律用**：`uv run --no-project python <脚本>`（需要时前缀 `PYTHONUTF8=1`）。
脚本只用标准库——加第三方依赖前先问，别默认 `pip install`。

## 令牌（红线）

猎聘令牌只从 `~/.workbuddy/mcp.json` 读（`mcpServers.liepin-mcp.headers.x-user-token`），
在 `liepin.py` 的 `load_endpoint()` 里取，注入到请求头。
**只读、不复制、不落盘、不打印、不进 git。** 不要把令牌写进本目录任何文件，也不要加「方便调试」的打印。
配置缺失要显式报错退出，不许降级猜测。

## 安全闸门（不可绕过）

1. `apply.py` 不带 `--confirm` 绝不外呼。**不要自作主张加 `--confirm`**——投递不可逆，
   必须由用户本人确认清单之后才执行。验证改动用 dry-run。
2. 单轮投递上限默认 15（`config.json: max_per_round`）。不要为了让流程跑完而临时放大。
3. 台账 `ledger.csv` 是投递去重的**唯一真源**，判断只走 `store.applied_ids()`，
   不要在别的脚本里重写一份——漂移的后果是重复投递。
4. 结果判不出就记 `unknown`，**且不写台账**。宁可漏记（可人工补），不可假记（会让岗位被永久排除）。
5. 抓取/接口失败一律显式报错。禁止 `except: pass`，禁止静默降级成 0 分或「没搜到」。
6. 搜索认证/网络失败必须向上传播——不能伪装成「市场没有岗位」。
7. 用户说「你替我挑一个」时，**按匹配度取第一**（`shortlist.py` 已降序排好，就是名单第一行），
   不另加偏好、不跳过外包/交付类岗位。用户 2026-09-23 明确指定了这条；
   要用别的口径挑，先问。

## 两条会反复犯的错

- **判不出来就说判不出来。** 不要把「查不到」写成「不存在」，不要把「页面 200」当成
  「岗位还在招」，不要把猜测写成原因。报事实（HTTP 状态、字节数、标题、原始响应），不给猜测性结论。
  同理，**不要把协议层的状态码当业务结论**：投递回包的 `errCode` 在「应聘成功」和
  「应聘失败: 您已投递过该职位！」两种情形下**都是 0**（2026-09-23 两种都实测到了）。
  结论只能看 `data.result` 里的中文，且先判失败标记再判成功标记。
- **别让字段名错位。** 池里存的是 `jobType`，投递接口要的是 `jobKind`——在 `shortlist.py` 里
  显式改名，不能直接把池行扔给 `write_rows`（缺列会被静默写成空值）。
  同理：过滤器要判断**最终被消费的那个字段**，不是中间字段。

## 数据 vs 产品

产品文件（`*.md`、`scripts/`、`config.json`）可以进版本库；
**真实数据绝不能进**：`pool/`、`ledger.csv`、`shortlists/`（含真实公司名/岗位名/链接）。
新脚本开始写某个真实数据文件时，同一次改动里把它加进 `.gitignore`。
配了 `matcher: embedding` 意味着把 JD 正文发给第三方，属于不可逆的对外披露，必须先征得用户同意。

## 用户自己维护的两处

- `criteria.md`：打分关键词与权重，是打分的唯一真源。要改口径改这里，不要改脚本里的默认值。
- `config.json`：搜索词、城市、每词页数、每轮上限。

改这两处不需要问，但改完要说明会影响什么（比如加宽关键词会引入更多非产品岗噪声）。

**改动 `criteria.md` 或 `config.json` 的 `matcher` 会让全池已有的分数失效。** 这件事由脚本
自己兜：`pool/jobs.csv` 的 `criteriaFp` 列记录每行分数是按哪一版口径算的（`matcher.fingerprint()`
= 解析后词表+权重的短哈希，**不哈希文件字节**，所以改注释/调行序不该触发重算）。
`score.py` 把「旧口径」和「没有分数」一样当作待处理并自动重算；`shortlist.py` 直接排除旧口径的行
并打印数量。两条都不要绕过：

- 不要在 `shortlist.py` 里把旧口径的行放回候选（会产出新旧口径混排的名单，肉眼分不出哪行是旧的）。
- 不要手工去写 `criteriaFp`（它只有一个出处：`score.py` 打分成功的那一刻）。
- 新增写入池子的字段时，别忘了 `search.py: build_row()` 也要补上该键——缺键会被
  `store.write_rows` 拦下（这是好事，别去放宽那个检查）。

## 别做的事

- **绝不要在仓库内任何位置跑 `git clean -fdx` / `git clean -fdX`。** 这是唯一会删掉真实数据的
  git 命令。仓库根是 `ai_pm_portfolio`，在根目录跑同样会删掉 `job_seeking/` 下的数据。
  2026-09-23 在临时仓库实测过边界：`git reset --hard`、`git checkout` 老提交、
  甚至 `git clean -fd`（**不带** `-x`）都**不会**动这些被忽略的文件——只有带 `-x`/`-X` 的
  `clean` 会删，而且删完恢复不了（它们从没被跟踪过，不在任何提交里）。
  之所以危险，是因为 `pool/`、`ledger.csv`、`shortlists/` 在这个工作区里就是**唯一的一份**：
  没有远端、没有副本，重建要重新花猎聘搜索额度。要用 `git status --ignored` 看它们，
  不要清理它们。真要腾空间，先整目录拷到仓库外再动手。
- 不要参考本机其它求职项目（`~/WorkBuddy/job_seeking/`、`~/.workbuddy/career-facts/`、
  其它仓库里的同类技能）来「对齐」本项目的设计——这是从头另起的项目。
- 不要提交 `_probe/`、临时抓取的 HTML、跑分产物。
- 不要给用户没要求的「优化」：不要加硬门槛一票否决、不要加简历生成、不要加数据库——
  当前形态是用户明确选定的。
